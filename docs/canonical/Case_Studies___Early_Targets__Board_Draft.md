## How to read these cases

1. **Problem / number / mechanism / ask** (McKinsey one-pager form).  
2. **Scenarios** use **placeholder compression factors** until the sealed metric card is signed.  
3. **Savings = f(memory spend × effective capacity gain × applicability fraction).**  
4. HYBA fee doctrine: **25% of measured savings** (only after measurement).  
5. Mining is **not** used as customer proof.

**Applicability fraction (critical honesty):** PULVINI applies to **structured / compressible working sets**, not 100% of all memory. Cases show sensitivity at 20% / 40% / 60% of memory-related spend in scope.

## Case A — Hyperscaler (AWS / Azure / GCP class)

### BLUF

Memory-bound AI and caching fleets can defer CAPEX and cut memory TCO if structured working sets compress under PULVINI; commercial engagement is gain-share on **measured** savings, not a SaaS seat.

### Problem

Hyperscalers face rising memory intensity (LLM KV-cache, in-memory stores, analytics shuffles) while DRAM, power, and data-centre footprint constrain growth. Industry commentary and earnings narratives repeatedly identify **memory and data movement**, not raw FLOPs alone, as binding constraints. *(External market figures must carry named sources on final export — e.g. hyperscaler CAPEX guidance, analyst notes; do not ship orphan $T figures.)*

### Mechanism

| Layer | Offer |
| --- | --- |
| Company | HYBA Data |
| Product | HERMES |
| Engine | PULVINI φ-folding on eligible working sets |
| Ops | Salamander self-heal / self-optimise (implemented; SLA separate) |
| Commercial | 25% of **measured** savings; no maintenance fee |

### Illustrative economics (sensitivity — not a quote)

Assume a hyperscaler business unit with **$1.0B/year** memory-related TCO in scope (hardware + power allocation). Eligible fraction of that TCO for structured compression: **f**. Effective capacity multiplier on eligible set: **m** (sealed later; show 1.5× / 2.0× / 2.6×).

Rough savings model (order-of-magnitude):

`Annual savings ≈ $1.0B × f × (1 − 1/m)`

| f  m | 1.5× | 2.0× | 2.6× |
| --- | --- | --- | --- |
| 20% | $67M | $100M | $123M |
| 40% | $133M | $200M | $246M |
| 60% | $200M | $300M | $369M |

HYBA fee at 25% of measured savings (illustrative): **$17M–$92M/year** on this unit, only if measurement confirms m and f.

### What we will not claim externally yet

- 6.94× / 7.155× / 85.4% as universal fleet multipliers
- Specific $95M/1,000-server claims without customer telemetry
- 99.999% uptime without sealed pack

### Ask

90-day measured pilot on one memory-bound service (KV-cache or cache tier): baseline → HERMES/PULVINI → savings report → gain-share term sheet.

### Proof plan (Tier path)

T2 internal benchmarks on customer-like traces → T3 production pilot telemetry → commercial seal.

## Case B — Enterprise multi-cloud user (Fortune 500 / regulated enterprise)

### BLUF

Enterprises overpay for cloud memory and ops complexity; HYBA Data reduces eligible memory footprint and automates heal/optimise loops under CIaaS — not another SaaS console.

### Problem

- Cloud bills grow faster than business value (memory-heavy analytics, Redis/Spark, vector/AI features).
- Talent shortage for continuous tuning.
- Multi-cloud policy without multi-cloud intelligence.

### Mechanism

Same stack as Case A; deployment **strategy** spans major clouds (AWS/Azure/GCP class). Provider certificates issued as evidence seals.

### Illustrative economics

Enterprise unit: **$50M/year** cloud spend; **30%** memory-related; **f = 40%** of memory-related eligible; **m = 2.0×** on eligible.

- Memory-related: $15M
- Eligible: $6M
- Savings at 2.0×: $3M/year
- HYBA 25%: **$0.75M/year** (illustrative)

Sensitivity: if m only 1.5× → savings $2M → fee $0.5M; if m 2.6× → savings ~$3.7M → fee ~$0.9M.

### Ask

Single-cloud pilot first (one provider, one workload class), then multi-cloud expansion once availability evidence is sealed.

### Proof plan

FinOps baseline + HERMES install + weekly savings dashboard + gain-share invoice test.

## Case C — Sovereign / national AI infrastructure

### BLUF

Sovereign programmes need computational efficiency and autonomy without permanent foreign ops dependency; HYBA Data offers compression + self-healing intelligence under local control — category CIaaS, not SaaS tenancy.

### Problem

- National AI CAPEX is large; memory and power dominate TCO.
- Sovereignty requires local operation, auditability, and reduced dependency on foreign managed services.
- Talent and ops capacity are scarce.

### Mechanism

| Need | HYBA Data response |
| --- | --- |
| Efficiency | PULVINI on eligible sovereign workloads |
| Autonomy | Salamander self-heal / optimise |
| Trust | Scrutiny / evidence receipts; claim boundaries |
| Commercial | Gain-share on measured savings; no maintenance rent |

### Illustrative economics

Sovereign programme memory TCO in scope: **$500M/year**. f = 30%; m = 2.0×.

- Eligible: $150M
- Savings: $75M/year
- HYBA 25%: **$18.75M/year** (illustrative)

### Governance note

Sovereign deals require separate legal, security, and data-residency packs. Mining and experimental IIT/consciousness narratives are **out of scope** for this case.

### Ask

Sovereign sandbox: classified-or-restricted workload class, offline-capable deployment path, joint measurement protocol, then production option.
