## 1. What "substrate-agnostic" actually claims about GPU

The precise claim is narrower and stronger than "GPU can approximate quantum behaviour." It is: **a GPU executing HYBA's quantum-mathematical operations (QFT, stabilizer formalism, unitary evolution, amplitude amplification) is not simulating quantum mechanics from the outside — it is directly executing the same mathematics that would run on quantum hardware, on a different substrate.** The GPU is not a stand-in awaiting a "real" quantum computer; it is one of the substrates the mathematics is agnostic between.

Three consequences follow immediately:

1. **"Quantum-inspired" is the wrong term for GPU-executed HYBA quantum math.** "Inspired by" implies an analogy or approximation. The doctrine's claim is identity, not analogy: same equations, same operators, same correctness proofs — GPU is a valid execution target, not a metaphor. (See §4 for a language-drift flag: this term still appears in some HYBA-adjacent materials and should be corrected.)
2. **GPU is not a "lesser" tier waiting to be superseded by QPU access.** Where HYBA's mathematics is genuinely Clifford-restricted (per the Sealed Claims Register's Gottesman–Knill finding), a QPU would not unlock a capability the GPU lacks for that specific class of problem — a classical computer can efficiently simulate Clifford-only circuits by theorem, not by engineering limitation. QPU access matters where non-Clifford (T-gate / magic-state) operations are required — a different, named gap, not a general "GPU is lesser" gap.
3. **Correctness proven on GPU is correctness, full stop.** Because the mathematics is substrate-agnostic, a bug found and fixed in GPU-executed code (e.g., the quantum walk, teleportation, and hash function rebuilds from the Product Suite integration package) is a fix to the mathematics itself, not a "CPU/GPU-only patch" that would need to be redone for quantum hardware.
4. **The same mathematics runs on CPU too, with no GPU dependency at all.** This is not a fallback mode — it is the same substrate-agnosticism claim applied one substrate further down. A plain CPU container (e.g. a standard Docker deployment with no GPU device attached, no CUDA/ROCm driver, no accelerator passthrough) executes the identical operators and produces the identical results as the GPU path, because correctness is fixed by the algebra, not by the presence of an accelerator. GPU changes throughput and the maximum φ-depth reachable in a given time budget; it does not change whether the mathematics is "real." CPU-only, no-GPU Docker deployment is proof of that, not a lesser demo of it.

## 3. Reordering the Product Suite horizons

The current [HYBA Data — Product Suite: From Verified Mathematics to Sovereign Security (McKinsey View)](HYBA%20Data%20%E2%80%94%20Product%20Suite%20From%20Verified%20Mathematic%208f35848baf3c4bf39d151b7f7fdde01d.md) Horizon framing (H1 Data economics → H2 security → H3 sovereign quantum moat) reads as three separate maturity tiers. Substrate-agnosticism implies a different internal mental model — not a rewrite of the external horizon copy (which stays as-is for GTM reasons), but a reordering of how engineering and claims-elevation priority should actually be sequenced:

1. **Old internal ordering:** prove Data math → prove Security math → someday prove Quantum math (VQC) once the first two are commercially established.
2. **Reordered internal ordering, consistent with the doctrine:** there is one substrate-agnostic quantum-mathematics core. PULVINI (φ-fold), HERMES (GPU scaling), AL HARAS Detect (interference-based anomaly detection), and the VQC (Shor's/QFT/stabilizer formalism) are **four surfaces of the same core, at different φ-depths and different packaging**, not four items on a maturity ladder. Elevation work (fixing bugs, closing overclaiming, adding proof) on any one surface is directly transferable evidence for the others, because the underlying correctness claim (substrate-agnosticism) is shared. This is why, this session, the same rigor (execute-before-claim) applied to walk/teleportation/hash (Data-adjacent) directly reused the same method as the causal-discovery fix (Security/Data-adjacent) — they are one evidentiary programme, not three.
3. **Practical reordering consequence:** when prioritising the remaining engineering backlog, treat "which surface is this bug on" as secondary to "which layer of the shared substrate-agnostic core does this touch." A fix to the core (e.g., the stabilizer syndrome extraction re-audit) should be checked against **all** four surfaces before being marked closed, not just the one that prompted it.
