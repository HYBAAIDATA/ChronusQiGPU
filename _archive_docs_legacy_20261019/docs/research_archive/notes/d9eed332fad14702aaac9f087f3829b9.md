<callout icon="🧭" color="blue_bg">
	**Objective:** execute the already-implemented qualification tooling against one immutable release candidate, preserve the resulting evidence, and promote readiness gates only when the corresponding real-world proof exists.
</callout>
## Operating rule
**Implementation is not qualification.** A script, simulation, checklist, compile result, or document must never be treated as a passed readiness gate. Every gate requires its defined executed evidence from the exact release candidate and environment under review.

## Phase A — Release-candidate preflight
**Owner: implementation agent**
1. Begin from a clean checkout and record:
	```powershell
git status --porcelain
git rev-parse HEAD
git log -1 --format="%H%n%ad%n%s" --date=iso-strict
	```
2. Run the complete repository test suite using the project’s declared test command. Export JUnit/coverage artefacts where configured.
3. Compile-check every new Python script:
	```powershell
python -m py_compile scripts/run_staging_qualification.py
python -m py_compile scripts/run_resilience_drills.py
python -m py_compile scripts/run_infrastructure_chaos.py
python -m py_compile scripts/run_rollback_under_load.py
python -m py_compile scripts/run_phase_3_qualification.py
	```
4. Validate Phase 1 controls:
	```powershell
python scripts/validate_production_config.py --static
	```
5. Verify the staging scripts obtain credentials solely from `MIDAS_STAGING_ADMIN_TOKEN` and `MIDAS_STAGING_USER_TOKEN`; no token may appear in arguments, source, logs, test reports, or manifests.
6. Stop on any failure. Record the failure, root cause, corrective commit, and re-run result.
**Evidence required:** clean-working-tree output, commit SHA, test output, compile output, configuration-validation output, dependency/image build log.
## Phase B — Commit, build, and CI
**Owners: implementation agent + deployment owner**
1. Commit Phase 2 and Phase 3 as one auditable change set. Do not amend after CI begins.
2. Open a pull request with the release-candidate SHA, scope, and known limitations.
3. CI must run against the exact SHA and fail closed on:
	- complete test suite;
	- static production-control validation;
	- syntax/compile checks;
	- image build;
	- package/security scanning required by the pipeline.
4. Build an immutable image and record its digest. Tag names are references only; the digest is the deployment identity.
5. Store CI logs, JUnit reports, scan reports, SBOM/provenance artefacts, and image digest with the candidate evidence.
**Stop condition:** failed/missing CI, mutable image reference, or mismatch between deployed artifact and recorded digest.
## Phase C — Staging deployment readiness
**Owner: deployment owner**
1. Deploy the recorded image digest—not a rebuilt or `latest` image—to staging.
2. Inject dedicated least-privilege staging credentials through the secret store only.
3. Confirm one intended listener, intended port, TLS/proxy health, database/cache dependency health, and alert routing.
4. Confirm monitoring can collect the actual metric names/labels before enabling alert rules. Do not rename a rule or metric simply to produce a green dashboard.
5. Capture deployment event, environment identifier, image digest, and initial health/readiness results.
**Stop condition:** staging differs materially from the candidate configuration, secrets are exposed, or observability is unavailable.
## Phase D — Phase 2 application qualification
**Owner: exercise owner; observer required**
1. Set secrets only in the process environment:
	```powershell
$env:MIDAS_STAGING_ADMIN_TOKEN = "<dedicated-admin-staging-token>"
$env:MIDAS_STAGING_USER_TOKEN = "<dedicated-non-admin-staging-token>"
python scripts/run_staging_qualification.py --base-url "https://staging.example.com"
	```
2. Run baseline, two-times-demand, spike, and soak workloads as defined in the Phase 2 protocol.
3. Verify, at minimum:
	- p95 \< 200 ms;
	- p99 \< 500 ms;
	- HTTP error rate \< 1%;
	- protected-route authentication/authorization behavior remains correct;
	- docs/OpenAPI production blocking remains correct;
	- request/correlation evidence and alert behavior are observable.
4. Preserve raw k6 output, JUnit/JSON reports, evaluator output, Prometheus screenshots/exports, logs, trace samples, and manifest hashes.
**Gate candidates:** Gate 4 performance, Gate 8 observability, and only the Phase 2 application-resilience controls actually exercised.
## Phase E — Phase 3 real infrastructure qualification
**Owner: exercise owner; approved change window, deployment owner, rollback owner, and observer required**
Run one drill at a time against the real staging deployment:
1. single API pod/process termination;
2. cache/Redis restart;
3. database failover/recovery, only with a tested restore path;
4. bounded network/dependency latency or outage;
5. resource pressure within explicit safety limits;
6. rollback under representative load.
For every drill record: hypothesis, safety boundary, start/end times, injected failure, observed alert, request behavior, data-integrity result, recovery time, rollback state, and evidence locations.
**Critical boundary:** simulations establish only simulation evidence. Only the approved real exercises can support Gate 5 resilience, Gate 6 chaos, and Gate 9 deployment evidence.
## Phase F — Evidence reconciliation and gate review
**Owners: implementation agent + observer + release authority**
1. Produce one evidence manifest tied to:
	- release commit SHA;
	- immutable image digest;
	- environment identifier;
	- CI run and artifacts;
	- test/load/chaos/rollback outputs;
	- alert/trace/log evidence;
	- approvals and unresolved findings.
2. For every gate, mark one of: `passed`, `failed`, `pending`, or `not exercised`.
3. A `passed` result must link to an executed test and its raw evidence. A missing or ambiguous artifact is `pending`, not assumed pass.
4. List remediations with owner, due date, corrective commit, and required re-test.
5. Update the readiness scorecard only after release-authority review.
## Phase G — Production decision
**Release authority only**
Production promotion remains blocked unless all required gates are evidenced and all high/critical findings are resolved or explicitly risk-accepted with time-bound controls. A passing staging package is necessary evidence—not a substitute for production approval.

```plain text
Release candidate: <commit SHA>
Image digest: <digest>
CI: PASS/FAIL — <run URL or artifact reference>
Staging deployment: PASS/FAIL — <environment>
Phase 2: PASS/FAIL/PENDING — <evidence manifest>
Phase 3 real drills: PASS/FAIL/PENDING — <exercise log>
Readiness gates proposed: <list, with evidence links>
Open findings: <owner, severity, required corrective action>
Production decision: BLOCKED / READY FOR APPROVAL
```
## Non-negotiable stop conditions
- untracked/dirty release candidate;
- failed or incomplete CI;
- secret/token exposure;
- deployment/image digest mismatch;
- unavailable observability;
- failed security boundary, data-integrity, or rollback check;
- missing approval, observer, or evidence record for a real infrastructure drill.
