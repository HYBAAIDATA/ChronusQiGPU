# Service ownership and intended contracts

## Verified implementation vs proposals

`workspace.openapi.json` describes the implemented evaluation endpoint. The
existing guardian authenticates each request before the adapter rechecks
admission and scopes jobs to tenant+actor. This is not organisation SSO, project
ACLs or a commercial entitlement service. `integrations.ts` exposes typed
unavailable boundaries; invoking one rejects without network traffic. No missing
service URL is inferred and no second database/backend/ledger is introduced.

The following are **intended contracts for owner review**, not claims that an
endpoint exists. Owners must provide canonical field names and semantics before
runtime adapters are added. Use owner-issued stable IDs, never display names as
keys. Version schemas, use opaque cursors for mutable enterprise inventories,
filter/sort server-side, return correlation IDs and safe error codes. Apply
server-side role + organisation + resource-policy checks on every read/write.
For consequential writes, bind an idempotency key to the authenticated principal,
operation and canonical request; persist both the outcome and operation record.
Conflicting reuse is a conflict, unknown acknowledgement is not failure.

## Entity map and retention authority

| Entities | Intended source of truth and relationships | Lifecycle / access / retention |
| --- | --- | --- |
| Organisation, customer account, user, membership, team, role | Approved identity/customer owner; membership joins a user to an organisation, roles scoped to resources | Invite/active/revoked under owner policy; organisation-admin permission, no implicit cross-tenant reads; identity owner sets retention |
| Workspace, project | Workspace service; project belongs to organisation/workspace, team grants refer to canonical identities | Create/edit/archive with version checks; project ACLs, approved activity retention |
| Contract, entitlement | Commercial authority; contract belongs to customer, entitlement references effective contract/version | Draft/approved/effective/expired/suspended semantics owner-defined; approval separation and immutable historical versions |
| Allocation, instance/execution resource | Capacity authority; allocation references entitlement + inventory resource | Recoverable lifecycle, quota/isolation definitions and audit; no instance definition is approved yet |
| Job, result | Existing TURING native facade; current pilot registry only tenant+actor, not project/customer linkage | Current five native states; process-local; report immutable on return, approved Theseus retention required for enterprise |
| Usage fact | Execution meter, bound to job/contract/measurement version | Immutable fact/correction; approved retention; not generated by browser or inferred from qubit count |
| Invoice reference | Hermitten/financial authority; linked to rated usage and billing account | Financial retention and corrections under billing owner; no local invoice authority |
| Audit event | Existing guardian for request decisions; each future owner for domain changes | Append-only approved custody; permissioned read/export, privileged actions auditable, retention/residency owner-approved |

Do not add parallel customer, user, ledger or invoice tables merely to satisfy a
screen. Map canonical equivalents once their actual owners are identified.

## Missing contract families

| Family | Intended request / response | Authentication, errors and recovery |
| --- | --- | --- |
| Enterprise identity/session | Owner session context -> stable subject, org memberships, granted scopes, expiry; invite includes org/email/role with approved delivery | Approved OIDC/SAML IdP only; MFA/recovery/domain verification/offboarding owned there; unauthenticated vs forbidden; no custom auth protocol |
| Membership/roles | List with cursor/filter; propose grant/revoke with subject, scope, role, expected version, reason -> audited operation | Organisation admin or constrained platform authority; reject escalation/foreign subjects; revocation checked server-side, test expiry |
| Projects/workspaces | Create/edit/archive with organisation, metadata, expected version; list cursor/search/sort; project jobs/results by canonical IDs | Project/org policy, deny foreign refs; archive not implied deletion; retention/deletion/legal-hold approval |
| Entitlement | Principal + operation + capability/resource request -> allow/deny with contract/version, limits and expiry | Commercial service authoritative; security subscription alone insufficient; denial/expired/restricted/capacity errors distinct and audited |
| Provisioning/inventory | Approved customer/contract/configuration/capacity/policy + reason + expected inventory version + key -> operation ID, last confirmed state and resource refs | Operator + approval rules; policy/capacity/version conflict; durable operation lookup/replay, compensations, verified final allocation; no browser optimistic activation |
| Metering | Signed/trusted immutable execution facts + delivery key -> stable ingestion acknowledgement or recoverable rejection | Workload authority not browser token; schema/version/unit/contract validation; duplicates acknowledged once; durable outbox and dead-letter owner |
| Rating/billing/reconciliation | Canonical usage refs + contract/rate version/effective period -> authoritative pending/rated status, statement/invoice refs, reconciliation differences | Billing-scoped read/write and approval separation; exact decimals/currency rules; version pinning and auditable corrections; no rerating history by editing UI |
| Custody/audit | Scoped lookup/export with cursor/time filters; store evidence under approved policy -> durable refs and integrity metadata | Same owner+purpose controls, time-limited support access; missing/gated evidence stays missing, retention/legal hold respected |
| Support/incidents | Scoped ticket/incident create/update with severity, safe summary, resource refs, reason/version -> incident ID/status/audit | Approved channel, retention and escalation; never unrestricted impersonation, grants expire/revoke and are auditable |

A schema must additionally define allowed fields, size bounds, rate limits,
timeouts, event order, eventual-consistency semantics, retry eligibility,
credential transport and redaction. Refuse unknown states rather than silently
mapping them to success. These proposals intentionally do not assign URLs or
pretend request/response field names are already an owner-approved API.

## Least-privilege proposal (requires owner approval)

- Platform operator: service health and constrained incident action, not rate approval.
- Service administrator: approved provisioning changes within delegated limits.
- Customer organisation administrator: own organisation membership and grants, not platform capacity/rates.
- Billing administrator: own financial references/exports, not arbitrary computation evidence.
- Project administrator: scoped project lifecycle/grants within organisation policy.
- Analyst/researcher: admitted jobs and permitted project evidence.
- Reviewer: read-only authorised evidence, no submission or cancellation.
- Support operator: approved purpose, scope and expiry; no blanket impersonation.

Test each grant via direct API calls and direct routes, including forged roles,
foreign IDs, stale sessions, removed membership and expired support grants.
Final role names and combinations belong to the approved business model.

## Hermitten reconnaissance outcome

Scoped connected-repository searches found historical Hermitten references, not
a verified executable billing API or sandbox. Only EuclidPhiEnterprise was
returned by the owner-scoped repository inventory. This is not proof that no
Hermitten system exists; it is an access/information gap. Obtain its actual
repository or versioned schema and sandbox before choosing reuse mechanisms.
Do not reinterpret AL HARAS's `hyba.security` subscription as a TURING contract,
convert lineage records into billing facts, or create invoices from job counts.

## Proposed usage and delivery model — NOT operational

`usage-event.proposed.schema.json` is a version-zero proposal for review, not a
Hermitten contract or deployed emitter. It keeps event/job/org/billing/contract
and capability refs, authoritative measurement quantity/unit/version, source
provenance and correction linkage. Quantities use exact decimal strings; no raw
program, bearer or result belongs in financial telemetry. Delivery/rating status
belongs in separately auditable processing records so the original fact remains
immutable. Optional project linkage requires an authoritative project mapping.

1. Execution authority commits a validated usage fact and durable outbox record
   atomically, or supplies an equivalently durable event source. If the source
   cannot guarantee this, stop commercial activation rather than use browser events.
2. Worker reads committed outbox, authenticates to the approved meter, validates
   version/unit/contract and delivers with stable event ID. Retry boundedly with
   backoff/jitter; an unreadable acknowledgement retains the same ID and fact.
3. Ingestion uniquely constrains event/source identity and payload digest; replay
   of the same fact returns the original acknowledgement, changed replay conflicts.
4. Rating pins contract/rate version and effective time, applies allowances and
   currency rounding under approved rules. Keep pending/unrated/rated separate.
5. Hermitten owns invoice/statement generation and canonical financial IDs.
6. Reconcile source -> outbox -> accepted -> rated -> invoiced records by stable
   IDs and exact totals, highlighting missing, duplicated, rejected, late or
   mismatched facts; retain explicit reconciliation runs and exception owners.
7. Corrections reference originals and approved reason/actor; never mutate past
   facts or silently retroactively change rates. Reconcile adjustment and invoice refs.

Required real-interface tests: duplicate/reordered/delayed delivery; lost ACK;
worker crash before/after commit and ACK; changed-payload replay; invalid unit;
expired/missing contract; rate version boundary; allowance exhaustion; rounding;
correction/credit; missing invoice; export permission; tenancy isolation; suspend
and terminate with unsettled usage. None is represented as passed.
