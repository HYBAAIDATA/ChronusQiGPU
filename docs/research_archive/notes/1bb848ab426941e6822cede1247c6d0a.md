## Address of Three Design Concerns
### 1. Chronicle Verification Latency → Merkle Checkpointing
**Problem:** `verify_integrity()` is O(n) — walks the entire predecessor-linked chain recomputing every hash. Under continuous dispatch this scales linearly.
**Solution:** Periodic Merkle checkpointing via `ChronicleCheckpoint`.
- Each checkpoint seals a verified accumulator hash at configurable intervals (default: every 1000 events, or on-demand via `create_checkpoint()`)
- `verify_from_checkpoint()` recomputes the accumulator for the sealed segment first (tamper detection), then verifies only new events from the last checkpoint forward: O(k) where k = events since checkpoint
- If no new events since checkpoint, returns (True, None) after accumulator verification — O(1)
- Checkpoint chain is itself hash-linked: each checkpoint's `predecessor_checkpoint_hash` references the prior checkpoint's accumulator
- Archived segments can be serialized separately; the checkpoint hash seals them immutably
- `compute_accumulator()` uses iterative Merkle tree construction over event hashes
**Operational guarantee:** The accumulator verification runs FIRST, before any early-return. Even with zero new events, a tampered sealed segment is detected.
### 2. Fail-Closed Veto Recovery → Organ Degradation State Machine
**Problem:** On veto, the CNS receives `(None, assessment, chronicle)` with no structural recovery path. The organ isn't marked, there's no fallback, and repeated vetos pile up silently.
**Solution:** Multi-layered veto recovery protocol.
**Degradation State Machine:**
- `HEALTHY` → `DEGRADED` (consecutive veto threshold reached, default 3)
- `DEGRADED` → `QUARANTINED` (further vetos without recovery, default 5)
- `DEGRADED` → `RECOVERED` (successful dispatch resets counter)
- `QUARANTINED` → requires explicit test dispatch to recover
**Fallback Routing:**
- On veto: record veto category, increment degradation counter
- Apply exponential backoff: `min(2^n, 300s)` for degraded, 3600s for quarantined
- Search for alternative organ in same domain (non-quarantined, past backoff window)
- If fallback found and clears confidence: dispatch to fallback, mark `FALLBACK_SUCCEEDED`
- If no fallback: escalate to CNS via veto category in assessment
**Backoff Registry:** Per-organ retry timestamps prevent immediate re-dispatch to degraded organs.
### 3. Epistemic Correction → Structural EvidenceSource
**This is the deepest correction.** The original gate used internal heuristics (execution_time \> 0, produced_at \> 0) and marked them as "passed" — conflating internal engineering checks with independent validation.
**Structural fix: ****`ValidationSignal`**** with ****`EvidenceSource`****.**
Every gate now returns a `ValidationSignal` carrying an `EvidenceSource` enum:
- `INTERNAL_HEURISTIC`: "The system's own checks passed — engineering evidence, not independent validation"
- `EXTERNAL_SUBSYSTEM`: "A wired independent subsystem has validated this result"
- `NONE`: No validation performed (vetoed assessments)
The `EvidenceSource` is a **mandatory field** of `ValidationSignal` — you cannot construct one without it. This is the mathematical representation: the evidence source is structurally inseparable from the pass/fail verdict.
**The feedback processing gate embodies this structurally:**
- Without external validator: returns `INTERNAL_HEURISTIC` with `signal_strength = 0.5` — deliberately low, because self-observation is weak evidence
- With external validator wired: returns `EXTERNAL_SUBSYSTEM` with `signal_strength = 1.0`
- The gate's reason string explicitly states "NOT independent validation" when internal
- `IntegrationAssessment` carries `EvidenceSource` per gate: `coherence_source`, `truth_source`, `causal_source`, `feedback_source`
- `all_external` property: True only if ALL four gates carry EXTERNAL evidence
- `any_external` property: True if at least one gate carries EXTERNAL evidence
**The system cannot "forget" that internal heuristics are internal.** The `EvidenceSource` is structurally encoded in the assessment. No result can claim external validation unless an external validator is wired AND returns positive.
## Task Orchestrator
### Architecture
```javascript
ResearchGoal → GoalDecomposer → Subtask DAG →
ExecutionScheduler → DelegationController → IntegrationAggregator →
GoalCompletionEvaluator
```
### Components
**GoalDecomposer:** Breaks a research goal description into a DAG of subtasks, one per domain. Supports domain-specific decomposition strategies via registered callables. Produces a `ResearchGoal` with `Subtask` nodes carrying dependency constraints.
**Subtask Dependencies:** Three modes:
- `REQUIRES_ALL` — all predecessors must succeed (default for linear research)
- `REQUIRES_ANY` — at least one predecessor must succeed (branching exploration)
- `OPTIONAL` — predecessors are informative only (parallel probes)
**ExecutionScheduler:** Topological execution respecting the DAG. At each step: find all subtasks with satisfied dependencies, execute via `DelegationController`, on veto retry with backoff, on success record and propagate.
**IntegrationAggregator:** Aggregates subtask results into a unified `AggregatedResult` capturing accepted/vetoed/fallback/failed breakdowns, evidence sources per subtask, and an aggregated hash.
**GoalCompletionEvaluator:** Evaluates whether goal meets acceptance criteria: completion ratio threshold, critical subtask survival, external evidence requirement (configurable).
### Pipeline
```python
orchestrator = TaskOrchestrator(controller)
goal, aggregated, passed, reason = orchestrator.execute(
    "Probe PHI-Space O(log N) search boundary",
    domains=[
        ResearchDomain.MATHEMATICAL_ENGINE,
        ResearchDomain.EMERGENCE_ENGINE,
        ResearchDomain.COHERENCE_EVALUATOR,
    ],
)
```
